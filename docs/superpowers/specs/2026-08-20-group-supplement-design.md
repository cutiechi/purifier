# 阅读页分组补全与操作面板尺寸调整

## 1. 背景与目标

当前 Purifier 的分组功能允许用户将帖子手动归入同一分组，但上游（cool18）存在一种常见模式：楼主在主帖发「第一章」，随后在跟帖（回复）里贴出「第二章」的链接。用户阅读时容易遗漏这些散落在跟帖里的续篇链接，导致分组不完整。

本设计要解决两个问题：
1. **阅读页主动检测跟帖中的相关帖子，一键补充分组**：用户在 `/read/:tid` 页面可主动触发检测，系统从跟帖中提取可能的相关帖子，经相似度筛选后，允许用户勾选并追加到当前帖子已属的现有分组。
2. **阅读操作面板尺寸调整**：当前 `ItemActions` Popover 面板宽度过窄（`w-72`），在补充分组等新功能加入后空间更紧张，需要适当加宽。

## 2. 触发条件与入口

### 2.1 入口位置

入口放在 `ItemActions` 的 Popover 菜单中，与「收藏」「刷新」「标签」并列，新增「补充分组」按钮。

### 2.2 显示条件

**仅当**当前帖子已属于某个分组时才显示该按钮。`useItemState` 扩展后返回的 `groupId` 存在即显示；`groupId` 为 `undefined` 时整个按钮不渲染。

### 2.3 交互流程

```
用户打开 /read/:tid
  → useItemState 返回 { ..., groupId: 5, groupTitle: "小说A" }
  → ItemActions Popover 中显示「补充分组」
  → 用户点击
    → 前端遍历 content.replies 提取候选 tid
    → 并行获取候选帖子标题
    → 计算相似度，筛选高相关候选
    → 展开候选列表面板
    → 用户勾选 → 确认
    → 调用 PUT /api/me/groups 追加成员
    → 成功：提示并刷新 ItemState
```

## 3. API 与数据层改动

### 3.1 扩展 `/api/me/state`

`GET /api/me/state?kind=post&id=<tid>&site=1`

**新增返回字段**：

```typescript
groupId?: number    // 所属分组 ID，无分组时省略
groupTitle?: string // 所属分组标题，无分组时省略
```

**后端实现**：在 `store.getState` 中追加查询：

```sql
SELECT g.id, g.title
FROM groups g
JOIN group_items gi ON gi.group_id = g.id
WHERE gi.tid = ?1
LIMIT 1
```

返回结果并入 `ItemState`。

### 3.2 扩展跟帖类型，保留站内链接

当前 `ReplyItem.subject` 经过 `stripHtml` 后纯文本化，`<a>` 标签及 `href` 丢失，前端无法从跟帖中提取帖子链接。

**类型扩展**（`packages/core/src/extractor/types.ts`）：

```typescript
export interface ReplyItem {
  tid: string
  uptid: string
  rootid: string
  uid: string
  username: string
  subject: string
  dateline: string
  size: number
  /** 从原始 subject HTML 中提取的站内 /read/:tid 链接 */
  links?: { tid: string; title: string }[]
}
```

**后端实现**（`Cool18Extractor.parseReplies`）：

在 `stripHtml(String(r.subject ?? ""))` 之前，先用 cheerio 解析原始 HTML，提取所有 `<a>` 标签中指向同站的链接，解析出 `tid` 和链接文本，写入 `links` 字段。提取逻辑复用现有 `extractLinksFromDom` 的链接过滤规则（只保留同站）。

### 3.3 新增 `GET /api/me/groups/:id`

现有 API 没有按 ID 获取单个分组详情的接口。前端在追加成员前需要知道分组的现有成员列表（`PUT /api/me/groups` 是全量 upsert）。新增：

```
GET /api/me/groups/:id
```

返回 `{ group }`，结构与 `listGroupsPage` 中的单条分组一致（含 `items` 成员列表）。后端直接复用已有的 `store.getGroup(id)`。

### 3.4 获取候选帖子标题

前端提取候选 tid 后，需要获取对应帖子的实际标题以做相似度比较。候选数量极少（通常 1-3 个），前端直接并行调用现有接口：

```
GET /api/posts?tid=<candidate>&site=1
```

取返回的 `title` 字段即可。该接口有内容缓存，命中时几乎无开销；数量少时对上游压力可控。不新增轻量 preview API，保持后端改动最小化。

## 4. 相似度检测算法（前端）

检测在用户点击「补充分组」后于前端本地执行，步骤如下。

### 4.1 提取候选 tid

遍历 `content.replies` 中所有跟帖：

1. **优先从 `links` 提取**：若 `reply.links` 存在，收集所有 `link.tid`。
2. **文本兜底正则**：从 `reply.subject` 中用正则提取：
   - `tid=(\d+)`
   - 独立数字序列 `\b\d{6,}\b`（cool18 tid 通常为 6 位以上数字）
3. **过滤**：
   - 去重（Set）
   - 过滤当前阅读帖子的 `tid`
   - 过滤已和当前帖子同属同一分组的 `tid`（前端先调用 `GET /api/me/groups/:groupId` 获取现有成员列表进行对比）

### 4.2 获取标题并计算相似度

对每个候选 tid：

1. 并行请求 `GET /api/posts?tid=<candidate>`
2. 请求失败的候选直接丢弃
3. 对当前标题 `A` 和候选标题 `B` 进行预处理：
   - 去掉装饰符号：`【】〖〗《》`
   - 统一空格、转小写
4. 计算相关度，满足以下任一条件即视为「相关」：
   - **共同前缀比例**：去掉末尾章节号/数字后，最长公共前缀长度 / min(len(A), len(B)) >= 0.5
   - **编辑距离比例**：Levenshtein 距离 / max(len(A), len(B)) <= 0.35
   - **关键词启发**：候选标题包含当前标题的「核心前缀」（前 6 个字符以上相同），且同时包含续篇关键词（`续|下|next|后续|下章|下一章|下回|第二章` 等）

### 4.3 阈值与兜底

- 至少相似度 >= 0.5 的候选才默认勾选；低于阈值但 > 0.3 的候选也展示，但默认不勾选，允许用户手动选择。
- 若无任何候选通过最低阈值（0.3），提示「未在跟帖中发现明显相关的帖子」。

## 5. 前端交互与组件

### 5.1 操作面板尺寸调整

`ItemActions` 的 Popover 内容区当前为 `w-72`（288px）。由于要新增「补充分组」按钮以及后续可能的扩展，面板宽度调整为：

```
w-80（320px）在 sm 以下
sm:w-96（384px）在 sm 及以上
```

同时保证内部表单控件（如标签编辑输入框）自适应宽度。

### 5.2 补充分组按钮

在 `ItemActions` 的 Popover 中，「收藏」和「刷新」之间插入新按钮：

```
[收藏]
[补充分组]  ← 新增，仅 groupId 存在时显示
[刷新]
[标签]
...
```

按钮文案旁可带一个小徽标，表示检测到多少个候选（如 `补充分组 (2)`），仅在候选已提取且 >0 时显示。

### 5.3 候选列表面板

点击「补充分组」后，Popover 关闭，页面内展开一个轻量面板。面板位置选择在操作按钮上方或正文底部浮动，推荐复用类似 `BookmarkList` 的展开模式或内联于 `ArticleView` 的 `footer` 区域上方。

面板内容：

- 标题：「补充分组 — 《分组标题》」
- 说明：「从跟帖中检测到以下可能相关的帖子：」
- 候选列表（每项一个 checkbox）：
  ```
  [x] 《小说A 第二章》  (tid=12345678)  相似度 87%
  [ ] 《另一本小说》    (tid=12345679)  相似度 42%
  ```
- 底部操作：「全选」「取消」「确认加入」

**加载状态**：检测过程中按钮或面板显示 `Spinner`，文字为「正在分析跟帖…」。

**空状态**：若无候选或全部过滤掉，面板显示「未检测到相关帖子」。

**错误状态**：若获取候选标题时部分失败，失败的候选不展示，面板顶部用小字提示「部分帖子获取失败，已跳过」。

### 5.4 追加确认与冲突处理

用户点击「确认加入」后：

1. 前端调用 `GET /api/me/groups/:groupId` 获取分组详情（含现有成员列表和 `key`）
2. 组装现有成员 + 新勾选成员的完整列表
3. 调用 `PUT /api/me/groups`
   - `key` 使用分组原 `key`
   - `title`/`author`/`genre` 保持原值不变
   - `items` 为完整成员列表 `{tid, title}[]`（upsert 覆盖）
4. 后端 `upsertGroup` 会检查一帖一组约束
5. 若某个候选 tid 已属于其他分组，后端返回 409 `tid already in another group`
6. 前端收到 409 时：
   - 若部分成功部分失败，提示「以下帖子已属于其他分组，无法加入：tid=xxx, tid=yyy」
   - 若全部冲突，提示「所选帖子均已属于其他分组」
   - 面板保持打开，用户可取消冲突项后重试

## 6. 错误处理与边界情况

| 场景 | 处理 |
|------|------|
| 当前帖子无分组 | 不显示「补充分组」按钮 |
| 跟帖为空 | 点击后提示「该帖子无跟帖」 |
| 跟帖无链接/无候选 tid | 提示「未检测到相关帖子」 |
| 获取候选标题全部失败 | 提示「无法获取候选帖子信息，请检查网络」 |
| 获取候选标题部分失败 | 展示成功获取的候选，顶部提示已跳过失败项 |
| 相似度均低于 0.3 | 提示「未发现明显相关的帖子」，同时展示低相似度候选（不默认勾选）供用户手动选择 |
| 候选 tid 已在其他分组 | 后端 409，前端单独提示冲突项，允许用户取消后重试 |
| 追加调用网络错误 | 面板保持打开，显示「加入失败，请重试」 |
| 用户取消面板 | 清空本次检测状态，关闭面板 |

## 7. 不涉及的范围

- **不新建分组**：需求明确只追加到现有分组。若当前帖子无分组，不提供此功能。
- **不自动创建分组**：不尝试从跟帖中自动创建新分组。
- **不修改搜索逻辑**：本设计与分组搜索无关，不改变 `listGroupsPage` 的搜索行为。
- **不实时监测跟帖更新**：检测基于当前页面已加载的 `content.replies`，不监听跟帖实时变化。

## 8. 测试要点

1. **后端**：`getState` 正确返回/不返回 `groupId`/`groupTitle`；`parseReplies` 正确提取/不提取 `links`；`GET /api/me/groups/:id` 正确返回分组详情。
2. **前端**：无分组时不显示按钮；有分组但跟帖无候选时正确提示空状态；相似度计算对典型标题对（如「第一章」与「第二章」）正确识别。
3. **集成**：一帖一组冲突时 409 处理正确；成功追加后 `ItemState` 或分组信息正确刷新。
4. **UI**：操作面板宽度在移动端和桌面端均显示正常；新增按钮不破坏现有 Popover 布局。
